# 需求分析规范：用户角色与访问模式

**文档类型**: 开发规则  
**版本**: v1.0  
**创建日期**: 2026-03-22  
**适用范围**: 所有Agent开发项目

---

## 1. 核心原则

**用户角色与访问模式必须在需求分析阶段明确，不得在开发过程中模糊或随意变更。**

---

## 2. 必须澄清的三大维度

### 2.1 用户角色清单

**问题清单**：
- 系统有哪些用户角色？
- 每个角色的职责是什么？
- 角色之间是否有权限差异？
- 是否有特殊角色（如管理员、审核员）？

**角色分类框架**：

| 维度 | 分类 | 说明 |
|-----|------|------|
| **使用场景** | 核心用户 | 直接使用系统完成主要任务（如教师） |
| | 辅助用户 | 间接使用或提供支持（如教研组长） |
| | 管理用户 | 系统管理和配置（如管理员） |
| **能力水平** | 专家用户 | 熟悉领域，需要高级功能 |
| | 普通用户 | 基础使用，需要引导 |
| | 初级用户 | 需要培训和简化流程 |
| **组织关系** | 独立用户 | 个人使用，无协作需求 |
| | 协作用户 | 团队协作，需要共享和同步 |
| | 层级用户 | 有上下级关系，需要审批和汇报 |

**必须明确的信息模板**：

```markdown
### 用户角色定义

| 角色ID | 角色名称 | 角色类型 | 使用频率 | 权限级别 | 主要任务 |
|-------|---------|---------|---------|---------|---------|
| UR-001 | 一线教师 | 核心用户 | 每日多次 | 完全权限 | 备课、授课、布置作业 |
| UR-002 | 教研组长 | 辅助用户 | 每周1-2次 | 查阅+审核 | 审核教案、统计教学效果 |
| UR-003 | 系统管理员 | 管理用户 | 按需 | 全权管理 | 用户管理、系统配置 |
```

---

### 2.2 并发访问模式

**问题清单**：
- 预计同时在线用户数量？
- 是否有高峰时段？峰值是多少？
- 用户会话时长是多少？
- 是否有批量操作场景？

**并发级别定义**：

| 并发级别 | 同时用户数 | 适用场景 | 技术要求 |
|---------|-----------|---------|---------|
| **单用户** | 1 | 个人工具、本地部署 | 无并发处理需求 |
| **小规模** | 2-10 | 小团队协作 | 基础锁机制 |
| **中规模** | 10-100 | 中等机构 | 需要连接池、缓存 |
| **大规模** | 100-1000 | 大型组织 | 需要分布式架构 |
| **超大规模** | 10000+ | 公共平台 | 需要微服务、负载均衡 |

**必须明确的信息模板**：

```markdown
### 并发访问需求

| 指标 | 数值 | 说明 |
|-----|------|------|
| 预计总用户数 | 100 | 学校总教师数 |
| 预计日活用户 | 50 | 约50%教师每日使用 |
| 预计峰值并发 | 20 | 备课前30分钟高峰 |
| 单用户会话时长 | 30分钟 | 平均备课时长 |
| 高峰时段 | 工作日7:00-8:00, 13:00-14:00 | 备课集中时段 |
```

### 2.3 交互访问模式

**问题清单**：
- 用户是独立访问还是需要交互协作？
- 是否需要实时同步？
- 数据是否需要共享？
- 是否有离线使用需求？

**交互模式分类**：

| 模式 | 描述 | 技术影响 |
|-----|------|---------|
| **独立访问** | 每个用户独立使用，数据不共享 | 无需数据同步，简单存储 |
| **单向共享** | 用户可查看他人数据，但不能修改 | 需要权限控制，只读接口 |
| **双向协作** | 多用户可同时编辑和同步 | 需要实时同步、冲突解决机制 |
| **异步协作** | 用户分时段协作，有审批流程 | 需要工作流引擎、消息队列 |
| **混合模式** | 部分独立，部分协作 | 需要灵活的权限系统 |

**必须明确的信息模板**：

```markdown
### 交互访问需求

| 场景 | 访问模式 | 涉及角色 | 数据需求 | 实时性要求 |
|-----|---------|---------|---------|-----------|
| 个人备课 | 独立访问 | 一线教师 | 个人教案库 | 无 |
| 教案审核 | 异步协作 | 一线教师 → 教研组长 | 共享教案 | 低 |
| 课堂授课 | 独立访问 | 一线教师 | 教案、课件 | 中 |
| 学生答题 | 双向协作 | 一线教师 ↔ 学生 | 答题记录 | 高 |
```

## 4. 设计影响分析

### 4.1 架构设计

| 场景 | 推荐架构 | 关键技术 |
|-----|---------|---------|
| 单用户独立访问 | 单体应用 | 简单存储、本地文件 |
| 小规模协作 | 单体+数据库 | 关系型数据库、基础锁 |
| 中规模协作 | 分布式应用 | Redis缓存、连接池 |
| 大规模协作 | 微服务架构 | 消息队列、实时同步 |

### 4.2 技术选型

| 需求 | 技术选项 |
|-----|---------|
| 实时协作 | WebSocket、WebRTC |
| 离线使用 | PWA、IndexedDB、本地缓存 |
| 权限控制 | RBAC、ABAC |
| 数据同步 | OT算法、CRDT |

## 5. 常见错误与解决方案

### 错误1：角色模糊

**问题**：只说"教师"，未区分一线教师、教研组长、名师

**后果**：功能设计不聚焦，权限混乱

**解决方案**：在需求文档中列出所有角色及职责

### 错误2：并发估算错误

**问题**：假设单用户，实际需要支持多用户

**后果**：出现资源竞争、数据不一致

**解决方案**：在需求阶段明确并发数，提前设计锁机制

### 错误3：交互模式未定义

**问题**：用户期望协作，系统设计为独立访问

**后果**：需要重构架构

**解决方案**：在需求阶段定义每个场景的交互模式

### 错误4：权限边界不清

**问题**：谁可以看、谁可以改、谁可以删未明确

**后果**：安全问题、数据泄露

**解决方案**：使用RBAC模型，明确每个角色的权限矩阵

## 6. 示例：完整的用户分析章节

以下是一个需求文档中用户分析章节的完整示例：

```markdown
## 5. 用户角色与访问分析

### 5.1 用户角色

| 角色ID | 角色名称 | 角色类型 | 数量 | 使用频率 | 权限级别 |
|-------|---------|---------|------|---------|---------|
| UR-001 | 一线教师 | 核心用户 | 100 | 每日多次 | 完全权限 |
| UR-002 | 教研组长 | 辅助用户 | 10 | 每周1-2次 | 查阅+审核 |
| UR-003 | 系统管理员 | 管理用户 | 2 | 按需 | 全权管理 |

**角色职责**：

- **一线教师**：独立备课、搜索资源、生成教案、使用课件、布置作业
- **教研组长**：审核教案、查看教学统计、提供反馈建议
- **系统管理员**：用户管理、角色分配、系统配置、数据备份

**权限矩阵**：

| 功能 | 一线教师 | 教研组长 | 系统管理员 |
|-----|---------|---------|-----------|
| 创建教案 | ✅ | ✅ | ✅ |
| 编辑教案 | ✅ 自己的 | ❌ | ✅ |
| 删除教案 | ✅ 自己的 | ❌ | ✅ |
| 审核教案 | ❌ | ✅ | ✅ |
| 用户管理 | ❌ | ❌ | ✅ |

### 5.2 并发访问

**并发需求**：

| 指标 | 数值 | 说明 |
|-----|------|------|
| 总用户数 | 100 | 学校总教师数 |
| 日活用户 | 50 | 约50%教师每日使用 |
| 峰值并发 | 20 | 备课前30分钟高峰 |
| 单用户会话时长 | 30分钟 | 平均备课时长 |
| 高峰时段 | 工作日7:00-8:00, 13:00-14:00 | 备课集中时段 |

**技术应对**：

- 数据库连接池：≥20
- Redis缓存：缓存热点教案数据
- 请求限流：每用户每分钟最多10次请求

### 5.3 交互访问模式

**场景-模式映射**：

| 场景 | 访问模式 | 涉及角色 | 数据需求 | 实时性 | 离线支持 |
|-----|---------|---------|---------|-------|---------|
| 个人备课 | 独立访问 | 一线教师 | 个人教案库 | 低 | ✅ 支持 |
| 教案审核 | 异步协作 | 一线教师 → 教研组长 | 共享教案 | 低 | ⚠️ 部分支持 |
| 课堂授课 | 独立访问 | 一线教师 | 教案、课件 | 中 | ✅ 支持 |
| 学生答题 | 双向协作 | 一线教师 ↔ 学生 | 答题记录 | 高 | ❌ 不支持 |
| 教学统计 | 单向共享 | 教研组长 | 全校数据 | 低 | ✅ 支持 |

**数据共享规则**：

- 教案默认私密，只有本人可见
- 提交审核后，教研组长可查看
- 通过审核的教案，同科组教师可查看
- 系统管理员可查看所有数据
```

## 7. 变更管理

### 7.1 角色变更流程

1. **发起变更**：明确新角色的职责和权限
2. **影响评估**：评估对现有功能和数据的影响
3. **架构评审**：评估是否需要调整架构
4. **更新需求**：更新需求文档中的角色定义
5. **同步开发**：通知开发团队进行相应调整

### 7.2 并发变更流程

1. **监控预警**：监控实际并发数是否接近设计上限
2. **容量规划**：评估是否需要扩容或优化
3. **架构调整**：必要时调整架构（如引入分布式）
4. **性能测试**：验证调整后的性能
