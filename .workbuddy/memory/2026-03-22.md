### 7. 设计数据持久化方案 ⭐（2026-03-22 晚新增）
创建了 `数据持久化方案设计_PostgreSQL.md`，包含：

**方案概述**：
- **采用PostgreSQL单库方案**（替代PostgreSQL + Redis + MongoDB）
- 理由：简化技术栈、降低运维成本、功能完备、性能满足

**数据库选型分析**：
1. **替代MongoDB**：使用JSONB类型 + GIN索引
   - 适用数据：授课日志、互动记录、用户配置
   - 性能：简单查询1-3ms，复杂查询10-30ms
2. **替代Redis缓存**：使用UNLOGGED表 + pg_prewarm
   - 适用数据：频道状态、在线用户列表
   - 性能：读取1-3ms，写入3-5ms，吞吐量10K ops/s
3. **替代消息队列**：使用普通表 + SKIP LOCKED + LISTEN/NOTIFY
   - 适用数据：异步任务队列、频道消息广播
   - 性能：消息延迟10-50ms，吞吐量1-5K msg/s
4. **替代实时通信**：使用LISTEN/NOTIFY + 触发器
   - 适用场景：频道消息广播、通知推送
   - 性能：消息延迟10-50ms

**数据分类与存储策略**：
- 核心业务数据（LOGGED表）：用户、教案、课件、习题、学情
- 实时缓存数据（UNLOGGED表）：频道状态、在线用户、热点课件
- 日志/审计数据（分区表）：授课日志、互动记录、系统日志
- 文档数据（JSONB列）：授课日志详情、互动记录详情、用户配置
- 队列数据（普通表 + SKIP LOCKED）：异步任务队列、频道消息队列

**数据库Schema设计**（12个核心表）：
1. users - 用户表
2. lesson_plans - 教案表
3. courseware - 课件表
4. channels - 频道表 ⭐
5. channel_members - 频道成员表 ⭐
6. channel_cache - 频道状态缓存表 ⭐（UNLOGGED表）
7. channel_messages - 频道消息表 ⭐
8. exercises - 习题表
9. test_papers - 试卷表
10. student_answers - 学生答题表
11. student_learning_records - 学情数据表
12. job_queue - 任务队列表

**索引设计**：
- B-tree索引：等值查询、范围查询、排序
- GIN索引：JSONB、数组、全文搜索
- BRIN索引：时间序列、分区表
- 部分索引：频繁查询的子集

**性能优化策略**：
- 连接池配置（psycopg2.pool）
- 批量操作优化
- 查询优化（EXPLAIN ANALYZE）
- 分区表优化（授课日志按月分区）
- 物化视图优化（定期刷新）

**备份与恢复**：
- 逻辑备份（pg_dump）
- 物理备份（pg_basebackup）
- 定期备份脚本
- 持续归档（Point-in-Time Recovery）

### 8. 评估仅使用PostgreSQL的可行性 ⭐（2026-03-22 晚新增）
创建了 `仅使用PostgreSQL可行性评估.md`，包含：

**评估结论**：✅ **对于AI教师Agent项目（1000+并发用户），仅使用PostgreSQL是可行且推荐的方案。**

**评估维度**：
1. **功能完整性**：✅ 关系数据、文档数据、缓存/会话、消息队列、实时通信、全文搜索全部满足
2. **性能对比**：
   - 缓存性能：读取1-3ms（Redis <1ms），吞吐量10K ops/s（Redis 100K ops/s）✅ 可接受
   - 消息队列：延迟10-50ms（Redis <10ms），吞吐量1-5K msg/s（Redis 100K msg/s）✅ 可接受
   - JSON查询：简单查询1-3ms（MongoDB <1ms），复杂查询10-30ms（MongoDB 5-10ms）✅ 可接受
3. **并发能力**：
   - PostgreSQL最大连接数可调至数千
   - 使用pgbouncer连接池管理1000+并发用户
4. **数据一致性**：
   - 单库ACID保证，无需分布式事务
   - 缓存一致性自动保证
5. **运维成本**：数据库实例-67%、备份策略-67%、监控指标-67%、故障排查-67%
6. **开发效率**：依赖管理+50%、代码复杂度+40%、事务处理+60%、查询优化+30%

**关键风险**：
- 超高并发（>5000用户）：概率低，影响高 → 引入Redis缓存
- 消息队列瓶颈（>10K msg/s）：概率低，影响中 → 引入RabbitMQ
- JSON查询慢（复杂聚合）：概率中，影响低 → 异步处理
- UNLOGGED表数据丢失：概率低，影响中 → 有恢复机制

**扩展路径**：
- 阶段1（< 1000用户）：PostgreSQL单库
- 阶段2（1000-5000用户）：PostgreSQL主库 + Redis缓存
- 阶段3（5000-10000用户）：PostgreSQL主从 + Redis集群
- 阶段4（> 10000用户）：微服务 + PostgreSQL集群 + Redis + 专用组件

**最终建议**：
✅ **推荐采用PostgreSQL单库方案**
- 从PostgreSQL单库起步
- 根据实际使用情况逐步扩展
- 保留扩展路径，按需引入Redis等组件

### 用户确认的重要需求

4. **并发性能优化**：支持1000+学生同时在线
5. **消息延迟要求**：课件同步<100ms，答题统计<500ms

### 需求分析教训
1. **并发访问模式必须在需求阶段明确**：
   - 单用户？小规模并发？大规模并发？
   - 是否需要实时同步？
   - 延迟容忍度是多少？
2. **实时性要求分级**：
   - 极高（<100ms）：用户体验敏感的操作
   - 高（<500ms）：需要快速响应
   - 中（<1-5s）：可接受延迟
   - 低（异步）：后台处理
3. **技术方案必须与并发级别匹配**：
   - L1-L2：单机WebSocket即可
   - L3：负载均衡 + 消息队列
   - L4-L5：微服务架构 + CDN + 弹性伸缩

### 数据持久化方案决策 ⭐
1. **简化技术栈**：仅使用PostgreSQL，无需Redis、MongoDB
2. **功能完备**：PostgreSQL 16+具备JSONB、LISTEN/NOTIFY、事务性队列等功能
3. **性能满足**：对于1000+并发用户，PostgreSQL性能完全满足
4. **ACID保证**：保证数据一致性，无需分布式事务
5. **成本效益**：单数据库方案降低基础设施成本
6. **灵活扩展**：可根据需要逐步引入Redis等组件
