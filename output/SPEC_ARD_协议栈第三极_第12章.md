## 一、定位与动机

### 1.1 现有问题

当前 12.6 节 "MCP + A2A 协议栈" 覆盖了 MCP 和 A2A 两个协议，但没有 ARD。这意味着：
- 读者知道怎么"调用工具"（MCP）和"委托 Agent"（A2A），但不知道"怎么找到这些资源"
- "先选协议，再选框架"（前言核心观点）缺少发现层——实际上应该是三层协议
- ARD 于 2026 年 6 月发布（Google + Microsoft + Hugging Face 联合工作组），时效性极强，加入本书是一个重要的竞争力卖点

### 1.2 为什么放在第 12 章

第 12 章是"生态工具"——ARD 是协议生态的基础设施，不是 Agent 治理机制。它解决的是"发现"问题，属于整个 Agent 生态的入口层。

12.6 节从 "MCP + A2A 协议栈" 扩展为 **"MCP + A2A + ARD：协议栈三剑客"**，形成完整的协议分层叙事：

```
ARD（发现层）── "有什么可用？怎么找到？谁提供的？可信吗？"
  ↓
A2A（协作层）── "Agent 之间怎么委托任务？怎么协商？怎么交付？"
  ↓
MCP（执行层）── "怎么调用具体工具和资源？怎么传递上下文？"
```

### 1.3 ARD 的独特性

ARD 与 MCP/A2A 有一个关键区别：**ARD 不参与执行**。它"坐在调用之前"——帮 Agent 决定"该调用谁"，然后退场。这种位置感需要在本节中反复强调。

##### 12.6.3.1 问题：Agent 怎么知道"有什么可用"？

用故事切入——不要"首先，ARD 是什么"：

> 假设你的编排 Agent 接到一个任务："帮我做一份 2026 Q2 的销售分析报告"。
>
> 它需要调用：一个数据查询 Agent（拉销售数据）、一个可视化 Agent（画图表）、一个文案 Agent（写分析文本）。
>
> 问题是：**它怎么知道这三个 Agent 的存在？** 它怎么找到它们？怎么判断哪个数据查询 Agent 更好？怎么知道它们是可信的？
>
> 2025 年之前，这个问题没有标准答案。你只能"手动配置"——把每个 Agent 的 URL 硬编码到编排器的配置里。10 个 Agent 还能管，100 个呢？1000 个呢？
>
> ARD 就是把"手动配置"变成"自动发现"的协议。

##### 12.6.3.2 四阶段发现流程

用一个清晰的流程图展示 ARD 的完整工作流程：

```
阶段一  阶段二        阶段三          阶段四
发布 → 索引构建 →    动态搜索 →      调用执行
│       │              │               │
│       Registry 爬取  │  编排器发送    │  编排器用 A2A/MCP
│       ai-catalog.json│  POST /search  │  调用选中的资源
│       构建语义索引    │  获取匹配列表   │
│                      │               │
Well-Known URI         语义向量匹配    ARD 退场
静态清单                + 联邦路由      具体协议接管
```

每个阶段的详细说明：
- **阶段一（发布）**：资源提供者在自己的域名下发布 `/.well-known/ai-catalog.json`
- **阶段二（索引）**：Registry（发现服务）爬取清单，构建语义向量索引
- **阶段三（搜索）**：编排 Agent 向 Registry 发送自然语言搜索请求，获得匹配的资源列表（含相关性评分）
- **阶段四（调用）**：编排 Agent 根据匹配结果，用 A2A 或 MCP 等协议调用选中的资源。ARD 的任务到此结束。

##### 12.6.3.3 Well-Known URI：在域名下埋线索

- 标准路径：`https://{domain}/.well-known/ai-catalog.json`
- AI Catalog 清单的核心结构展示（简化 JSON 示例）
- 条目必填字段：`identifier`（URN）、`type`（IANA Media Type）、`url` 或 `data`（二选一）
- 条目关键可选字段：`description`、`capabilities`、`representativeQueries`、`tags`
- 四种发现入口（不止 Well-Known URI）：
  - Well-Known URI：`/.well-known/ai-catalog.json`（最核心）
  - robots.txt：`Agentmap: https://example.com/catalog.json`
  - HTML `<link>` 标签：`<link rel="ai-catalog" href="...">`
  - DNS SVCB 记录：`_catalog._agents.example.com`
- `representativeQueries` 的巧妙设计：2-5 个自然语言查询示例，Registry 用它构建语义向量嵌入——这让自然语言搜索成为可能

##### 12.6.3.4 URN 标识符：每项资源的"身份证号"

- 格式：`urn:air:<publisher>:<namespace>:<agent-name>`
- 逐段解析：`urn`（固定前缀）→ `air`（Agentic AI Resource 命名空间）→ `publisher`（FQDN，组织信任锚点）→ `namespace`（可选层级，按部门/团队分类）→ `agent-name`（资源名称）
- 设计意图分析：
  - 逻辑身份与物理位置解耦——换了托管平台不影响发现
  - FQDN 作为信任锚点——`acme.com` 的资源天然全局唯一
  - 联邦合并无碰撞——不同组织的同名 Agent 不会冲突
- 示例：`urn:air:salesforce.com:crm:lead-enrichment` → Salesforce 的 CRM 部门提供的线索增强 Agent

##### 12.6.3.5 联邦搜索：跨 Registry 的联合发现

- 为什么需要联邦？——一个 Registry 不可能索引全世界的所有 Agent
- 三种联邦模式对比：

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| `auto` | Registry 自动查询上游，合并返回统一结果 | 用户不想关心"结果从哪来" |
| `referrals` | Registry 返回自身结果 + 其他 Registry 的引用，客户端自行跟进 | 客户端需要控制搜索范围和优先级 |
| `none` | 仅搜索自身索引 | 企业内部 Registry，不暴露给外部 |

- 实际案例（回扣开头的销售报告场景）：
  - 编排 Agent 先搜企业内部 Registry（数据查询 Agent + 文案 Agent）→ federation: none
  - 企业内部没有可视化 Agent → 切换到 federation: referrals → 找到公共 Registry 里的可视化 Agent

##### 12.6.3.6 Trust Manifest：谁提供的不重要，可不可信才重要

- ARD 中 `score`（搜索相关性评分）≠ 信任评分——这两个维度是分离的
- Trust Manifest 的组成部分：
  - `identity`：加密身份标识（SPIFFE ID / DID / HTTPS URI）
  - `attestations`：合规认证列表（SOC2、HIPAA、GDPR 等）
  - `provenance`：来源血缘链（从哪里衍生/发布）
  - `signature`：Detached JWS 签名
- 设计哲学：信任评估是独立于搜索的——搜索回答"有没有"，Trust Manifest 回答"能不能用"
- 企业场景：合规团队可以根据 Trust Manifest 中的 SOC2 认证自动过滤供应商

##### 12.6.3.7 三协议协作全景

用一个完整的端到端场景串联 ARD → A2A → MCP：

> 回到我们的销售报告任务。
>
> 1. 编排 Agent 向企业 Registry 发送 `POST /search { text: "销售数据查询 + 可视化 + 报告撰写" }`（**ARD**）
> 2. Registry 返回三个匹配的 Agent Card 引用（数据 Agent / 可视化 Agent / 文案 Agent）
> 3. 编排 Agent 通过 Agent Card 中的 URL 获取详细信息（**A2A 发现**）
> 4. 编排 Agent 向数据 Agent 发送 `SendMessage`："拉取 2026 Q2 销售数据"（**A2A 任务**）
> 5. 数据 Agent 内部通过 MCP 调用公司数据仓库的 SQL 查询工具（**MCP**）
> 6. 数据 Agent 将结果作为 Artifact 返回给编排 Agent（**A2A 交付**）
> 7. 编排 Agent 将结果传给可视化 Agent → 生成图表 → 传给文案 Agent → 生成报告

这个场景让读者直观理解三层协议各自在什么时刻介入。
