### 1.2.1 从问题出发：为什么需要设计模式？

假设你的Agent已经上线，最初只用OpenAI。某天，老板说：
> "我们要支持国产模型，用户可以选择用文心一言还是GPT。"

如果直接写代码，你可能会这样：

def call_llm(provider, prompt):
    if provider == "openai":
        import openai
        response = openai.ChatCompletion.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )
        return response.choices[0].message.content
    
    elif provider == "wenxin":
        import wenxin

        response = wenxin.call(
            model="ERNIE-Bot",
            prompt=prompt  # 注意：它用的是prompt参数
        )
        return response.result
    
    elif provider == "claude":
        import anthropic
        # Claude的接口又不一样
        response = anthropic.Client().messages.create(
            model="claude-3",
            messages=[{"role": "user", "content": prompt}],

        return response.content[0].text

你的业务逻辑里充满了供应商的细节：

### 🎯 设计模式登场：适配器模式

#### 核心思想：统一接口，隔离变化

**类比理解**：
- 你的手机充电器是"适配器"：把220V交流电转换为5V直流电
- 你不需要关心电是怎么发的，只需要USB接口
- 换一个充电器，手机照样用

**代码演进**：

**第一步：定义统一接口**

```python
from abc import ABC, abstractmethod

# 就像定义"所有充电器必须有USB接口"
class BaseLLMClient(ABC):
    """LLM客户端的统一接口"""
    
    @abstractmethod
    def chat(self, prompt: str) -> str:
        """发送对话，返回文本"""
        pass
```

**第二步：为每个供应商实现适配器**

```python
# OpenAI适配器
class OpenAIAdapter(BaseLLMClient):
    def __init__(self, api_key):
        self.client = openai.OpenAI(api_key=api_key)
    
    def chat(self, prompt: str) -> str:
        # 把统一的接口转换为OpenAI特有的调用
        response = self.client.chat.completions.create(
            model="gpt-3.5-turbo",
            messages=[{"role": "user", "content": prompt}]
        )
        return response.choices[0].message.content

# 文心一言适配器
class WenxinAdapter(BaseLLMClient):
    def __init__(self, access_token):
        self.token = access_token
    
    def chat(self, prompt: str) -> str:
        # 把统一的接口转换为文心一言特有的调用
        response = wenxin.call(
            model="ERNIE-Bot",
            prompt=prompt
        )
        return response.result

# Claude适配器
class ClaudeAdapter(BaseLLMClient):
    def __init__(self, api_key):
        self.client = anthropic.Client(api_key=api_key)
    
    def chat(self, prompt: str) -> str:
        # 把统一的接口转换为Claude特有的调用
        response = self.client.messages.create(
            model="claude-3",
            messages=[{"role": "user", "content": prompt}],
            max_tokens=1024
        )
        return response.content[0].text
```

**第三步：业务代码不再关心细节**

```python
# ✅ 业务代码清爽了
def handle_user_question(user_input: str, llm_client: BaseLLMClient):
    # 业务逻辑清晰可见
    return llm_client.chat(user_input)

# 使用
openai_client = OpenAIAdapter(api_key="...")
wenxin_client = WenxinAdapter(access_token="...")

result1 = handle_user_question("你好", openai_client)
result2 = handle_user_question("你好", wenxin_client)
```

#### 收益对比

| 维度 | 不用适配器 | 用适配器 |
|------|-----------|----------|
| 业务代码 | 充满if-else | 清晰简洁 |
| 添加新供应商 | 修改多处 | 新增一个类 |
| 单元测试 | 必须调真实API | 可Mock |
| 代码行数 | 少 | 稍多（值得） |

### 🎯 进阶：工厂模式

#### 新问题：谁来创建适配器？

现在业务代码清爽了，但谁来决定用哪个适配器？

```python
# ❌ 又出现了if-else
def get_llm_client(provider: str) -> BaseLLMClient:
    if provider == "openai":
        return OpenAIAdapter(api_key=os.getenv("OPENAI_KEY"))
    elif provider == "wenxin":
        return WenxinAdapter(access_token=os.getenv("WENXIN_TOKEN"))
    elif provider == "claude":
        return ClaudeAdapter(api_key=os.getenv("CLAUDE_KEY"))
```

#### 解决方案：工厂模式

**核心思想：把创建对象的逻辑封装起来**

```python
class LLMClientFactory:
    """LLM客户端工厂"""
    
    @staticmethod
    def create(provider: str) -> BaseLLMClient:
        """根据配置创建对应的客户端"""
        
        # 从环境变量读取密钥
        config = {
            "openai": {
                "api_key": os.getenv("OPENAI_KEY")
            },
            "wenxin": {
                "access_token": os.getenv("WENXIN_TOKEN")
            },
            "claude": {
                "api_key": os.getenv("CLAUDE_KEY")
            }
        }
        
        # 创建对应的适配器
        if provider == "openai":
            return OpenAIAdapter(**config["openai"])
        elif provider == "wenxin":
            return WenxinAdapter(**config["wenxin"])
        elif provider == "claude":
            return ClaudeAdapter(**config["claude"])
        else:
            raise ValueError(f"Unknown provider: {provider}")

# 使用
client = LLMClientFactory.create("openai")
result = client.chat("你好")
```

#### 更进一步：配置驱动

把映射关系放到配置文件：

```yaml
# config/llm_providers.yaml
providers:
  openai:
    class: OpenAIAdapter
    env_key: OPENAI_KEY
  wenxin:
    class: WenxinAdapter
    env_key: WENXIN_TOKEN
  claude:
    class: ClaudeAdapter
    env_key: CLAUDE_KEY
```

```python
# 工厂实现
import yaml

class LLMClientFactory:
    _registry = {}
    
    @classmethod
    def load_config(cls, config_path: str):
        """从配置文件加载供应商映射"""
        with open(config_path) as f:
            config = yaml.safe_load(f)
        
        for name, provider_config in config["providers"].items():
            # 动态导入类
            module_name, class_name = provider_config["class"].rsplit(".", 1)
            module = importlib.import_module(module_name)
            cls._registry[name] = getattr(module, class_name)
    
    @classmethod
    def create(cls, provider: str) -> BaseLLMClient:
        """动态创建客户端"""
        if provider not in cls._registry:
            raise ValueError(f"Unknown provider: {provider}")
        
        adapter_class = cls._registry[provider]
        return adapter_class()  # 各适配器自己读取环境变量
```

#### 收益

- ✅ 添加新供应商：只需修改配置文件
- ✅ 业务代码：完全不知道具体实现
- ✅ 符合开闭原则：对扩展开放，对修改关闭

### 📚 设计模式总结

#### 适配器模式
- **解决的问题**：接口不兼容
- **核心思想**：定义统一接口，适配不同实现
- **何时使用**：需要对接多个第三方系统

- **何时使用**：需要根据配置动态创建对象

#### 组合使用的威力
- 适配器：解决"怎么调用"
- 工厂：解决"谁来创建"
- 组合：构建灵活、可扩展的系统

```markdown
### 10.3 治理架构设计：从混乱到有序

#### 问题场景：监控的困境

你的多智能体系统已经上线，有10个Sub-Agent在协作。某天，成本突然暴增：

> 老板："为什么今天花了$500？昨天才$50！"

你需要排查，但发现：
- 每个Agent的日志格式不统一
- 有的Agent没有记录Token消耗
- 无法追踪一个请求经过了哪些Agent

#### 方案一：侵入式监控（❌）

在每个Agent里加监控代码：

```python
class SearchAgent:
    def run(self, query):
        # 监控代码混在业务逻辑里
        start_time = time.time()
        logger.info(f"SearchAgent started: {query}")
        
        try:
            result = self._do_search(query)
            token_count = self._count_tokens(result)
            cost = self._calculate_cost(token_count)
            metrics.record("search_agent", cost, time.time() - start_time)
            return result
        except Exception as e:
            logger.error(f"SearchAgent failed: {e}")
            raise

class CodeAgent:
    def run(self, requirement):
        # 又要写一遍类似的监控代码
        start_time = time.time()
        logger.info(f"CodeAgent started: {requirement}")
        
        try:
            result = self._generate_code(requirement)
            token_count = self._count_tokens(result)
            cost = self._calculate_cost(token_count)
            metrics.record("code_agent", cost, time.time() - start_time)
            return result
        except Exception as e:
            logger.error(f"CodeAgent failed: {e}")
            raise

# 问题：
# 1. 每个Agent都要写重复的监控代码
# 2. 修改监控逻辑，要改10个Agent
# 3. 业务逻辑被监控代码污染
```

#### 问题分析

| 问题 | 影响 |
|------|------|
| 代码重复 | 每个Agent都写一遍监控 |
| 难以维护 | 改监控逻辑要改多处 |
| 违反单一职责 | Agent既要干活又要监控 |
| 遗漏风险 | 新Agent可能忘记加监控 |

### 🎯 设计模式登场：中间件模式

#### 核心思想：拦截器链

**类比理解**：
- 机场安检：每个人都要经过安检通道
- 安检员不关心你要去哪，只负责检查
- 你可以添加多个安检环节（身份验证、行李扫描、金属探测）

**代码演进**：

**第一步：定义中间件接口**

```python
from abc import ABC, abstractmethod
from typing import Callable, Any

class Middleware(ABC):
    """中间件基类"""
    
    @abstractmethod
    def intercept(self, request: Any, next_handler: Callable) -> Any:
        """
        拦截请求
        :param request: Agent的输入
        :param next_handler: 下一个处理器
        :return: Agent的输出
        """
        pass
```

**第二步：实现具体中间件**

```python
# 日志中间件
class LoggingMiddleware(Middleware):
    def intercept(self, request, next_handler):
        print(f"[{datetime.now()}] Request: {request}")
        result = next_handler(request)  # 执行Agent
        print(f"[{datetime.now()}] Response: {result}")
        return result

# 监控中间件
class MetricsMiddleware(Middleware):
    def intercept(self, request, next_handler):
        start_time = time.time()
        result = next_handler(request)
        duration = time.time() - start_time
        
        # 记录指标
        metrics.record_duration(duration)
        metrics.record_tokens(result.token_count)
        return result

# 熔断中间件
class CircuitBreakerMiddleware(Middleware):
    def __init__(self, failure_threshold=5):
        self.failures = 0
        self.failure_threshold = failure_threshold
    
    def intercept(self, request, next_handler):
        if self.failures >= self.failure_threshold:
            raise Exception("Circuit breaker is OPEN")
        
        try:
            result = next_handler(request)
            self.failures = 0  # 重置失败计数
            return result
        except Exception as e:
            self.failures += 1
            raise
```

**第三步：构建中间件链**

```python
class AgentWithMiddleware:
    """带中间件的Agent包装器"""
    
    def __init__(self, agent, middlewares: list):
        self.agent = agent
        self.middlewares = middlewares
    
    def run(self, request):
        # 构建中间件链
        def handler(req):
            return self.agent.run(req)
        
        # 从后往前包装
        chain = handler
        for middleware in reversed(self.middlewares):
            chain = lambda req, mw=middleware, next_h=chain: mw.intercept(req, next_h)
        
        return chain(request)

# 使用
search_agent = SearchAgent()

# 包装Agent，添加监控
monitored_agent = AgentWithMiddleware(
    search_agent,
    middlewares=[
        LoggingMiddleware(),
        MetricsMiddleware(),
        CircuitBreakerMiddleware()
    ]
)

# 调用（Agent本身不需要关心监控）
result = monitored_agent.run("搜索AI相关的论文")
```

#### 执行流程

```
请求 → LoggingMiddleware → MetricsMiddleware → CircuitBreaker → Agent
                                     ↓
响应 ← LoggingMiddleware ← MetricsMiddleware ← CircuitBreaker ← 结果
```

#### 收益对比

| 维度 | 侵入式 | 中间件模式 |
|------|--------|-----------|
| 代码重复 | 每个Agent写一遍 | 中间件写一次 |
| 业务逻辑 | 被监控污染 | 保持纯净 |
| 扩展性 | 改多个Agent | 加一个中间件 |
| 灵活性 | 难以调整顺序 | 可自由组合 |

### 🎯 进阶：洋葱模型

中间件可以形成一个"洋葱"结构：

```
         请求进入
            ↓
    ┌──────────────────┐
    │  日志中间件       │
    │  ┌──────────────┐ │
    │  │ 监控中间件    │ │
    │  │ ┌──────────┐ │ │
    │  │ │ 熔断中间件│ │ │
    │  │ │ ┌──────┐ │ │ │
    │  │ │ │ Agent│ │ │ │
    │  │ │ └──────┘ │ │ │
    │  │ └──────────┘ │ │
    │  └──────────────┘ │
    └──────────────────┘
            ↓
         响应返回
```

**代码实现**：

```python
class OnionMiddleware:
    """洋葱模型中间件"""
    
    def __init__(self):
        self.middlewares = []
    
    def use(self, middleware: Middleware):
        """添加中间件"""
        self.middlewares.append(middleware)
    
    def execute(self, request, agent):
        """执行中间件链"""
        
        def create_handler(index):
            if index == len(self.middlewares):
                # 到达核心：执行Agent
                return lambda req: agent.run(req)
            
            # 递归构建中间件链
            middleware = self.middlewares[index]
            next_handler = create_handler(index + 1)
            
            return lambda req: middleware.intercept(req, next_handler)
        
        handler = create_handler(0)
        return handler(request)

# 使用
onion = OnionMiddleware()
onion.use(LoggingMiddleware())
onion.use(MetricsMiddleware())
onion.use(CircuitBreakerMiddleware())

result = onion.execute("查询", search_agent)
```

#### 中间件的执行顺序

```python
# 请求阶段：从前到后
LoggingMiddleware.before()  # 记录请求
    → MetricsMiddleware.before()  # 开始计时
        → CircuitBreaker.before()  # 检查熔断状态
            → Agent.run()  # 执行业务逻辑
        → CircuitBreaker.after()  # 记录结果
    → MetricsMiddleware.after()  # 记录指标
→ LoggingMiddleware.after()  # 记录响应

# 响应阶段：从后到前（洋葱剥皮）
```

```markdown
### 2.2.3 设计模式：策略模式在Prompt管理中的应用

#### 问题场景

你的Agent需要根据不同场景使用不同的Prompt模板：
- 用户提问 → 问答模板
- 代码生成 → 编程模板
- 数据分析 → 分析模板

如果直接写：

```python
def get_prompt(task_type, user_input):
    if task_type == "qa":
        return f"你是一个助手，请回答：{user_input}"
    elif task_type == "code":
        return f"你是一个程序员，请写代码：{user_input}"
    elif task_type == "analysis":
        return f"你是一个分析师，请分析：{user_input}"
```

又出现了if-else地狱！

#### 策略模式解决

```python
from abc import ABC, abstractmethod

# 策略接口
class PromptStrategy(ABC):
    @abstractmethod
    def build(self, user_input: str) -> str:
        pass

# 具体策略
class QAStrategy(PromptStrategy):
    def build(self, user_input: str) -> str:
        return f"你是一个助手，请回答：{user_input}"

class CodeStrategy(PromptStrategy):
    def build(self, user_input: str) -> str:
        return f"你是一个程序员，请写代码：{user_input}"

class AnalysisStrategy(PromptStrategy):
    def build(self, user_input: str) -> str:
        return f"你是一个分析师，请分析：{user_input}"

# 策略工厂
class PromptStrategyFactory:
    _strategies = {
        "qa": QAStrategy(),
        "code": CodeStrategy(),
        "analysis": AnalysisStrategy()
    }
    
    @classmethod
    def get_strategy(cls, task_type: str) -> PromptStrategy:
        return cls._strategies.get(task_type, QAStrategy())

# 使用
strategy = PromptStrategyFactory.get_strategy("code")
prompt = strategy.build("实现一个快速排序")
```

#### 为什么用策略模式？

- ✅ 新增任务类型：添加新策略类即可
- ✅ 策略可独立测试
- ✅ 运行时可动态切换策略
```

## 八、总结

### 核心改进思路

**不讲"是什么"，而是讲"为什么"**

从：
- ❌ "适配器模式是XXX"
- ❌ "工厂模式是XXX"

到：
- ✅ "遇到了XX问题，用适配器模式解决"
- ✅ "代码是这样演进的..."

### 最终目标

让读者：
1. **理解设计思想**：知道为什么要用这个模式
2. **掌握演进过程**：知道如何从问题推导到解决方案
3. **学会举一反三**：能在自己的项目中应用这些模式

### 关键成果

- 📈 降低理解门槛：从"看不懂"到"原来如此"
- 📈 提升学习深度：从"知道名称"到"理解本质"
- 📈 增强实用性：从"理论模式"到"实战应用"
